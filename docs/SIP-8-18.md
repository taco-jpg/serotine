# Sharing, direct delivery, profiles, and retention

This change implements SIPs 8, 9, and 11–18. SIP 10 (native app distribution) remains outside this release. The canonical proposals and their review statuses are maintained on the repository's `SIP` branch.

## Share selected messages — SIP 8

Choose **Select messages** in a conversation or text channel, check the messages to copy, then choose **Share selected**. Review the bundle, select an accepted conversation or writable channel, and confirm **Send shared copy**. Cancel sends nothing and leaves the original conversation unchanged.

A bundle contains at most 20 messages and an 8,000-character plain-text fallback. The selection is ordered by original timestamp with stable ID ties. It includes selected text, abbreviated sender addresses, timestamps, and optional file name/type/size. Attachment bytes, download capabilities, encryption keys, private local contact names, and optional profile fields are not copied. Polls become a plain question/options snapshot with no voter identities.

Private, secret, expiring, moderator-hidden, pending, failed, deleted, and already-shared messages cannot be selected. The service rechecks source and destination before sending; changed selections require a fresh preview. Nested bundles are not supported. File sharing within a bundle is metadata-only in this first release.

Shared content is a new signed encrypted message from the person sharing it. It is a quotation, not proof that the original authors wrote those words. It grants no access to the source conversation. Later edits or deletion of the original do not alter the copy. Shared copies cannot be edited in place.

Updated clients render a compact expandable bundle. Existing direct/group clients can display the exact plain-text fallback because it uses an ordinary message event. Older community clients with strict payload validation can reject the new optional structure safely; they require an update to display it.

## Force P2P — SIP 9

Force P2P is an explicit direct-conversation delivery choice. Both accepted contacts must enable it and keep Serotine open. The UI reports an authenticated, verified direct connection separately from ordinary online presence. A blocked or unavailable direct route leaves the draft unsent; there is no message relay, R2 attachment, or TURN fallback.

The initial feature set is encrypted one-to-one text and small file/image delivery. Direct files have a 2 MiB cap and use bounded chunks, integrity verification, acknowledgement, progress, cancellation, and direct retry. Unsupported relay-dependent controls are unavailable in this mode. Groups and communities continue to use their own delivery paths.

Short-lived authenticated setup records and STUN may assist connection establishment. They contain connection information, not conversation content. Direct connections can expose network addresses to the other participant. Local tests demonstrate the implementation's route restrictions; they do not establish that every pair of networks can connect.

Direct-only routing is signed into message events and preserved across local storage and backup restore. Changing modes cannot release an old direct-only outbox item to the relay. Previously received history can still be read locally. A deliberate new shared copy is a separate send action with an explicit destination preview; automatic retry and synchronization never create such copies.

AI summaries do not include direct-only history, including after switching back to ordinary delivery.

## Profiles and avatars — SIPs 11–12

Optional profiles are private by default. Open **Settings → Notification/privacy → Edit profile** for picture, banner, display name, about-me text, custom status, and profile colors, with previews. Pictures and banners support validated static images and GIF animation. Profile colors apply to the card and preserve readable controls independently of the app theme. Input images are limited to 4 MiB and 4096 × 4096 decoded pixels; processed avatars are at most 512 × 512, banners 1024 × 512, and each processed media item plus its still preview must fit 128 KiB. GIFs have an additional 80-frame, 20-second-per-loop limit and a decoded-pixel budget.

**Share with this friend** grants are separate for each field and each friend. The Add, Accept, and friend-menu **Profile sharing** controls expose all six choices, initially unchecked. The recipient receives only selected fields after an accepted relationship and compatible authenticated exchange; shared communities do not grant access. Local nicknames remain separate and are never distributed as profile data.

Changing or revoking a grant affects future delivery. Supported clients process versioned revocations and clear revoked displays. Blocking or removing a friend revokes grants; re-adding starts with unchecked choices. Previously downloaded copies and screenshots cannot be recalled, and an offline client can display an earlier version until it reconnects. Sharing permissions last six days and require an explicit renewal. Ordinary profile edits and device synchronization do not renew them. Expired or uncertain permission state disables disclosure until the owner chooses fields again; this bounds stale-device authority within the relay recovery window. Optional profile delivery pauses for Force P2P contacts without blocking other contacts.

Profile media travels through authenticated encrypted delivery. No optional field is published in an open profile directory or arbitrary remote image URL. Unsupported or invalid profiles use the generated identity fallback; images and display names are not identity verification.

## Group consent and receipts — SIPs 13–14

New private groups start with the administrator. Inviting another person creates a pending invitation with a seven-day lifetime, not membership. The invitee explicitly accepts or declines. Accepted direct contacts and friends are still required to accept the group invitation. Until acceptance is established, pending invitees receive no ordinary group traffic and are not shown as active members.

Administrators can revoke pending invitations and use the separate, confirmed **Dissolve group** action. Dissolution terminally invalidates the group and its invitations. **Leave group** affects an ordinary member only; local chat deletion and archive are separate actions. Old invitations, backups, or delayed acceptance cannot recreate a dissolved group. Legacy groups migrate through signed invitations; an updated client can automatically confirm only its own previously recorded explicit group acceptance or signed prior group message. Friendship alone never qualifies.

Group and community receive/read actions do not emit durable per-person social receipts. Senders see their own Pending, Sent, or Failed submission state. Local unread markers continue to work; direct-message receipts are unchanged. Attachment verification acknowledgements remain narrow storage-control events and are not reader lists.

## Server data lifetime — SIPs 15 and 18

New relay data is bound to authenticated retention scopes. Removing a direct contact ends server retention for the pair; both parties must explicitly accept a new relationship boundary before new relay-backed traffic resumes. Terminal group/community deletion closes the corresponding scope. The server records minimal terminal state before bounded cleanup, rejects stale submissions, and retries physical object deletion without reopening the scope.

Scopes omit names and message text. They enable correlation needed for lifecycle authorization; they do not make server metadata anonymous. Legacy data without a reliable conversation scope retains its previous retention policy because it cannot be safely attributed retroactively. This release does not retroactively purge those archives. Local history, exported backups, downloaded files, and screenshots are unaffected by server cleanup.

Attachments use server storage as a delivery buffer. A completion acknowledgement is sent only after the complete attachment passes integrity checks and is saved in a durable local cache. Generic delivered/read receipts cannot delete attachment bytes. Direct attachments are reclaimed after the intended recipient completes; private-group attachments wait for the required recipients or finite expiry. Fallback expiry is seven days for direct/private-group attachments and 30 days for community attachments.

After acknowledged cleanup, a device with the local file continues displaying it. A device that loses its cache cannot assume the server still has a copy. Missing/expired copies produce an unavailable state. Duplicate acknowledgements and cleanup are idempotent; old events and backups do not recreate deleted objects.

## Product continuity — SIPs 16–17

Landing and app surfaces share semantic themes, typography, controls, spacing, and motion tokens. Preset and custom themes remain supported. Motion explains state changes, keeps keyboard focus usable, and is reduced or removed under `prefers-reduced-motion`.

Inbox order uses meaningful message or creation activity, with stable identity-based ties. Opening, reading, changing settings, archiving/unarchiving, filtering, or restoring a route does not artificially promote a conversation. Route restoration still remembers the last view and channel separately. Real message activity can reorder keyed rows with a short positional transition.

## Validation and deployment

Run the repository unit suite, TypeScript, lint, focused browser scripts, production build, and Worker deployment dry run. Browser scripts use synthetic identities and local isolated state. They do not use real conversations or invoke an AI provider.

The local storage-v2 integration test uses real workerd, Durable Objects, D1, and R2. In its synthetic 32 KiB single-recipient case, completion after a simulated ten seconds reclaimed 32,784 stored bytes, wrote ten D1 rows including index maintenance, and made one R2 delete batch. A duplicate completion made zero D1 writes and zero R2 operations. These are measured test-case costs, not a production throughput estimate.

Different-network physical-device P2P connectivity remains a separate deployment acceptance check. Production account bindings and cleanup execution must also be checked in the deployed environment; a dry run does not publish or prove a live rollout. Before deploying, apply migrations through `0008_group_admission.sql` (including `0007_ephemeral_file_delivery.sql`) through the existing database migration command, preserve the D1/R2/DO bindings in `wrangler.toml`, and retain the five-minute scheduled cleanup trigger. Remote migrations and deployment are separate release actions.
